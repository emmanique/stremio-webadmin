## Transcoding policy telemetry fix

This release fixes a telemetry mismatch that made transcoding policy decisions appear absent in WebAdmin even when the FFmpeg policy wrapper was running.

The current wrapper emits profile-based records such as:

```text
[ffmpeg-policy] profile=vaapi-h264; video=libx264->h264_vaapi; decode=software; engine=vaapi
```

The previous dashboard parser only understood the older `mode=...` format. The parser now accepts both formats and exposes the effective profile decision through `latestDecision`, active-session `policyDecision`, and `policyTelemetry`.

Source-media codecs are still read from FFmpeg `Stream #` lines. In a profile record, the left side of `video=<old>-><new>` is the encoder target selected by the Stremio core before the execution profile override; it is not necessarily the media source codec.

## VAAPI pipeline correction

The native FFmpeg and HLS command builders now keep hardware-decoded VAAPI frames on VAAPI surfaces through pixel-format normalization, scaling and encode.

The previous no-scale path could combine VAAPI hardware decode with a software `format` plus `hwupload`, effectively asking FFmpeg to upload frames that were already hardware frames. Depending on the FFmpeg/driver path this could fail or introduce an unnecessary GPU/CPU transfer.

The corrected pipeline uses:

```text
scale_vaapi=format=nv12
```

or, when scaling is required:

```text
scale_vaapi=w=<width>:h=-2:format=nv12
```

Regression tests now explicitly verify that VAAPI transcoding does not insert `hwupload`, that NV12 normalization is present with and without scaling, and that a core `copy` decision never enables hardware decode accidentally.

## Important policy behaviour

The execution profile does not decide whether a stream must be transcoded. Stremio remains authoritative for the Direct Stream versus transcode decision. The fork profile changes the video execution pipeline only after Stremio has requested transcoding. A core `copy` decision is preserved to avoid unnecessary re-encoding, quality loss and GPU/CPU load.

If `executionProfile.id` is `legacy`, no explicit verified execution profile has been selected yet. Choose a runtime-verified profile in WebAdmin if hardware acceleration is expected.

Profiles are considered available only after a real runtime FFmpeg self-test. Merely having `h264_vaapi`, `hevc_vaapi`, `h264_nvenc`, `hevc_nvenc`, `libx264` or `libx265` compiled into FFmpeg is not treated as proof that the corresponding execution path works on the current host/container.

## End-to-end performance test

A host-side diagnostic is included:

```bash
python3 tools/platform_performance_test.py
```

It measures and validates:

- Stremio, WebAdmin, Pi-hole and Gluetun container health;
- container CPU, memory, network I/O, block I/O and process counts;
- concurrent HTTP throughput and p50/p95/p99 latency;
- DNS resolution from the Stremio namespace;
- Gluetun health in VPN mode;
- transcoding runtime readiness and selected execution profile;
- real encoder profile self-tests;
- FFmpeg wrapper policy instrumentation;
- optional synthetic 720p encoding performance;
- machine-readable JSON output for before/after comparisons.

See `docs/PERFORMANCE.md` for the full procedure and interpretation guidance.

## Update/package behaviour

Normal installation and updates remain package-based. The Server updater reads the fork version, pulls the matching immutable GHCR package, validates its advertised OCI version when present, activates only the Stremio runtime container, performs health validation and retains the previous image for rollback. WebAdmin and Pi-hole are not recreated by a Server-only update.
