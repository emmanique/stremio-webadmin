## VPN stability fix

This release fixes a Gluetun/CyberGhost restart loop observed after the VPN tunnel connected successfully.

### Fixed

- Gluetun now keeps its own resolver on `127.0.0.1:53`, preventing startup healthchecks from querying the bridge address before the built-in DNS server is ready.
- Pi-hole reaches Gluetun DNS through a private TCP/UDP DNS proxy on `172.30.0.10:1053`, which forwards only inside the VPN gateway to `127.0.0.1:53`.
- The default VPN LAN route list no longer includes broad `10.0.0.0/8`, because CyberGhost allocates `10.x` tunnel addresses and Gluetun documents that outbound subnets must not overlap the VPN tunnel range.
- Existing saved profiles containing the old `10.0.0.0/8` default are sanitised at VPN startup.
- CyberGhost OpenVPN runtime configuration now keeps one local `redirect-gateway def1` and ignores pushed duplicate `redirect-gateway` / `redirect-private` directives.
- Stremio waits for the Gluetun Docker healthcheck before starting in VPN mode.
- Trusted LAN HTTPS certificate bootstrap remains independent from VPN readiness and persists in the Stremio cache volume.

## DNS path

`Stremio -> Pi-hole 172.30.0.53 -> Gluetun DNS proxy 172.30.0.10:1053 -> Gluetun DNS 127.0.0.1:53 -> CyberGhost VPN`
