# Stremio Server WebAdmin 3.0.2

## Summary

3.0.2 is a patch release for HDR/PQ and tested Dolby Vision playback
through the browser/HLS server-transcoding path.

The transcoding decision remains client-path aware: direct/COPY playback
is not promoted to server transcoding by the VAAPI execution policy.
When the HLS path has already selected video transcoding for an HDR
source, AUTO VAAPI can now keep decoding, tone mapping and encoding on
the GPU.

The fix addresses HDR sources that expose BT.2020/PQ signalling but do
not expose mastering-display side data to the bundled FFmpeg. Source
colour properties detected by ffprobe are propagated explicitly to
FFmpeg before input processing so that `tonemap_vaapi` can perform the
HDR-to-SDR BT.709 conversion without failing with:

`No mastering display data from input`

## Fixes

- Propagate the probed video colour space as `colorSpace`.
- Preserve HDR/PQ/HLG source classification independently from the
  execution backend.
- Keep COPY/direct video decisions independent from AUTO VAAPI
  transcoding.
- For HDR sources already selected for AUTO VAAPI server transcoding,
  provide the detected source colour primaries, transfer characteristic
  and colour space to FFmpeg.
- Use the full VAAPI path for the validated HDR server-transcoding case:
  VAAPI decode -> `tonemap_vaapi` -> optional `scale_vaapi` ->
  H.264 VAAPI encode.
- Remove the slow software floating-point Hable tone-mapping fallback
  from this AUTO VAAPI path.
- Treat HDR/Dolby Vision HLS sources conservatively when the HLS client
  contract does not expose an HDR display-capability signal.
- Add dedicated HDR/Dolby Vision command-construction and regression
  coverage.

## Validation evidence

The HDR/Dolby Vision patch was rebased directly on the immutable
`v3.0.1` release commit before final validation.

Automated validation:

- focused HDR/transcoding regression: 33 tests passed;
- complete regression suite: 1374 tests passed, 11 skipped;
- `git diff --check` passed;
- legacy software Hable HDR fallback is absent from the AUTO VAAPI path;
- COPY remains a separate video execution path.

Runtime validation on Intel Iris Xe with `/dev/dri/renderD128` used the
bundled Jellyfin FFmpeg 4.4.1.

A tested 3840x1540 HEVC 10-bit BT.2020/PQ Dolby Vision Profile 8 source
with a base layer completed a controlled full-VAAPI conversion when the
detected source colour properties were supplied explicitly to FFmpeg.

The controlled 10-second conversion completed successfully at
approximately 58 fps / 2.38x speed when scaled to 1920x770 and encoded
to H.264 VAAPI.

This validation does not claim universal compatibility with every Dolby
Vision profile. The validated Dolby Vision scope of this patch is the
tested Profile 8 source with the base-layer characteristics described
above.

## Upgrade notes

Preserve the existing `.env` and all named Docker volumes.

3.0.2 is a coordinated release tag for the Server, WebAdmin and VPN
images. The upstream Server/Core remains at 1.6.20.

After publication, pin the coordinated images to `3.0.2`, validate the
configuration, pull the new images and recreate only the services
required by the normal upgrade procedure.

Existing Intel VAAPI installations retain the 3.0.1 `iHD` driver-name
normalization.

Never use `docker compose down -v` for this patch upgrade.
